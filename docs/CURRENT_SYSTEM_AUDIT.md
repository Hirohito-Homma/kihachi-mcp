## Integration breaks and documentation drift

1. The standalone music core, MCP product, AbletonGPT and old Studio are separate checkouts/surfaces. Code inspection did not find a single router that composes all four; the MCP runtime is the current product path and has a deterministic MIDI builder plus local Ollama intent interpretation.
2. Sol/Astra can interpret a production brief only after explicit Studio selection and cost authorization. Astra MIDI composition remains absent; the requested provider-neutral Composer is a new capability, not a model-name setting.
3. The current revision and Live state models do not carry the source note data needed for the promised precise revision of arbitrary existing Live MIDI.
4. Sample indexing is filename-oriented; sample selection and single-target replacement are not yet tied to a reviewed, undoable Live transaction.
5. `README.md` expects 29 MCP tools, while the current FastMCP registry exposes 37 after capability discovery and constrained MIDI composition were added; `docs/CURRENT_SYSTEM_STATUS.md` remains a historical 35-tool snapshot. The current full test run passes 626. Update public counts only from the live registry and current CI.
6. `docs/CURRENT_SYSTEM_STATUS.md` is a dated operational record, not a fresh observation. Its AbletonGPT connectivity warning and prior Live version/state need live revalidation before presenting current status.
7. No code was identified as definitively dead from bounded searches. The separate old Studio and separate music-core logic are overlap risks requiring ownership decisions before removal; do not delete either during integration.

## Recommended implementation route

Use `kihachi-mcp` as the product integration point and retain its current Studio and service boundaries. Do not make the separate music-core or AbletonGPT repositories runtime dependencies by importing their internals. Implement the first vertical slice in small, reversible increments: (1) add a capability matrix from the running Live bridge; (2) add a provider-neutral MIDI composer contract and a deterministic adapter, with optional OpenAI/Ollama adapters selected explicitly and no paid or model-download fallback; (3) extend revision data flow to retrieve and fingerprint only the selected managed Live clip’s exact notes, then alter note timing for syncopation while preserving all other notes; (4) expand sample metadata/indexing and add user-reviewed candidate preview and one-sample replacement; (5) verify the same plan and result through Fake transport before any human-authorized real-Live smoke test.

This route builds on the existing runtime and safety services. It avoids a UI rewrite, avoids resynthesizing the whole Set, and makes the requested Bass-only revision the first testable product milestone. It does not mark the mission complete until the final scripted scenario has passed in real Ableton Live.
