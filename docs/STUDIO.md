# KIHACHI 制作画面

日本語の制作指示から、ローカルAIでMIDI候補を作り、確認して Ableton Live の専用トラックへ適用します。

Cursor や Codex は不要です。有料APIには接続しません。モデルの自動ダウンロードもしません。

完全音声対話の最終設計と段階的な実装条件は [STUDIO_VOICE_DESIGN.md](STUDIO_VOICE_DESIGN.md) に記載しています。現在は短い音声入力と返答の読み上げを接続した段階で、自然な継続対話は開発中です。

制作画面の「KIHACHIと対話」では、マイクで最大12秒話し、聞き取った日本語を確認・修正してから対話へ送れます。誤認識に備えて対話への自動送信は初期状態でオフです。ユーザーが報告した「ミューテーションパンク」→「Mutation Funk」の補正では元の聞き取り結果も表示し、自動送信を選んでいても確認を待ちます。返答の日本語読み上げはこのMac内で生成します。音声認識にはMacのSpeech許可とブラウザのマイク許可が必要です。認識はオンデバイスを必須とし、利用できなければエラーにして文字入力を使います。案を採用するまで制作指示は変わらず、候補生成やLiveへの適用も始まりません。対象が曖昧な指示は聞き返します。実際の音声認識精度は未測定です。

## 起動

対話欄で「909のキックを探して」と入力すると、サンプル索引からファイル名の候補を最大5件表示します。「1番を詳しく」で保存場所と容量を確認できます。「909を探して」のように楽器が不明な場合は聞き返し、次の返答でも検索語を保持します。音色を解析した推薦・音源の取り込み・Live変更はこの検索に含まれません。

音声欄は起動時に日本語オンデバイス対応とmacOSの認識許可を読み取り、状態を表示します。この確認だけでは録音や許可要求はしません。未許可の場合、更新済みのローカル認識アプリでは「macOSの音声認識を許可」からOSの許可画面を開けます。許可後に録音が使えるようになります。OSの許可を変更した場合は「音声の準備状況を再確認」を押してください。初回認識時の許可操作が終わるまでは、認識品質を検証済みとは扱いません。

音声認識に失敗したときは、許可不足、録音データの読み取り失敗、認識時間切れ、聞き取り失敗を分けて表示します。許可状態の確認は文字起こしと同じMacアプリとして起動して行います。認識できなかった録音は一時領域から削除します。

macOSが複数の聞き取り候補を返した場合は、対話欄に別候補のボタンを表示します。候補を選んでも対話へ自動送信せず、発話欄を確認して「話しかける」を押します。候補が1つしか返らない場合はボタンを表示しません。候補は精度を保証するものではありません。

1. Ollama を起動し、導入済みのモデル（既定 `gemma4:latest`）があることを確認します。Ollama がなくても既定解釈で制作できます。
2. Ableton Live を開き、KIHACHI Live Device を1つ入れます。
3. 次のいずれかを実行します。

```bash
cd /Users/user/MusicAI/kihachi-mcp
uv run kihachi start
```

`uv run python -m kihachi_mcp.studio` でも同じです。または `scripts/kihachi-studio.command` をダブルクリックします。

4. ブラウザが `http://127.0.0.1:8765/` を開きます。

## 画面の使い方

1. 日本語で制作指示を入力します。
2. 「候補を生成」を押します。経過秒数が出ます。
3. 解釈、補った値、未対応の指示、セクション、ノート数を確認します。「指示ごとの反映」の「ジャンル既定で含む」は、その言葉を規則で読んだのではなく、選ばれたジャンルのパターンに元から入っている要素です。
4. 「プロジェクト」で SongSpec、構成（セクションごとの小節・エネルギー・パート）、トラックを確認します。保存済みの候補はここから開き直せます。
5. 「AIレビュー」の指摘を選んで修正案を作るか、「範囲を指定して修正を依頼」で対象と小節（例 33-49）を指定します。修正案は BEFORE / AFTER を見て「採用」するまで今の候補を変えません。採用すると新しい候補になり、修正履歴に残ります。
6. 「この候補を承認」。承認していない候補は Live へ送れません。
7. 「適用内容を確認」（ドライラン）で Tempo / Tracks / Clips / Notes / Arrangement と操作数を見ます。Live は変わりません。
8. 問題なければ「この内容でLiveへ適用」。1回だけ実行し、自動再試行はしません。
9. 送信後、Live から読み戻した値を計画と比べた `ABLETON VERIFICATION` が出ます。後から「Liveから読み戻して検証」で再確認できます。

画面の「完了」は、実際に終わった処理だけを指します。形式検査の合格を「良い曲」とは表示しません。`PROJECT READY` は Live が計画どおりの内容を返したことだけを意味します。

「システム（状態・設定・診断）」では、各部品の状態、AI の設定（導入済みモデルのみ選択可）、Ableton と保存先の情報を見られます。エラー時は上部の帯に原因と「再試行 / 設定 / 診断」が出ます。技術的な詳細は「開発者モード」をオンにしたときだけ表示します。画面の詳しい説明は [STUDIO_GUIDE.md](STUDIO_GUIDE.md)。

## 接続状態の見分け方

| 表示 | 意味 | 対処 |
| --- | --- | --- |
| Ollamaが起動していません | `127.0.0.1:11434` に届かない | `ollama serve` |
| 保存済みモデルが見つかりません | `gemma4:latest` がない | 手動導入済みモデルだけを使います。KIHACHIはダウンロードしません |
| Liveに接続できません | デバイス未配置、または返信ポート使用中 | Liveでデバイスを入れ、CursorのMCPサーバーが 17772 を掴んでいれば止める |
| デバイス版が一致しません / 状態取得がタイムアウト | Max側のJSが古い、または大きなSetの全取得 | `maxforlive/kihachi.device.js` をデバイスと同じフォルダへ置き、Maxで `reload` するかデバイスを入れ直す。必要な版は `kihachi-live-device/0.3.1` |

認証トークンは手元のハンドシェイクファイルで扱います。画面に貼る必要はありません。

## 参考音源ライブラリ

制作画面の「参考音源ライブラリを開く」または `/references` から使います。
手持ち音源・Freesound・Jamendoの音源を同じSQLite DBに保存できます。
取得済みファイルの取り込みはAPI認証なしで使えます。認証を設定すると公式APIで検索し、
作品を1件選んで取得・解析できます。Apple Musicからの抽出は実装していません。
外部へ送るのは検索語・作品IDと提供元に必要な認証情報だけで、手持ち音源や解析結果は送りません。

### 公式APIの設定

環境変数、またはGit外の `~/Library/Application Support/KIHACHI/reference-api.json` に
次のキー名で設定します。JSONファイルは所有者だけが読める権限（0600）にしてください。
別の設定ファイルは `KIHACHI_REFERENCE_API_CONFIG` で指定できます。環境変数を優先します。
キーやトークンの値を会話・UI・ログ・Gitへ貼らないでください。

- `FREESOUND_API_KEY`: 検索用APIキー。
- `FREESOUND_ACCESS_TOKEN`: OAuthアクセストークン。原音源の取得に必要で、検索にも使えます。
  APIキーだけの場合は検索のみ有効です。プレビュー音声を原音源の代わりに取り込むことはしません。
- `JAMENDO_CLIENT_ID`: 開発者アプリのClient ID。Client Secretとは別です。

設定ファイルはリクエスト時に読むため、値の更新だけならStudio再起動は不要です。
画面の「設定あり」は値の存在だけを示し、認証成功は実際の検索結果で確認します。
ローカル設定に `FREESOUND_CLIENT_ID`、`FREESOUND_REFRESH_TOKEN`、
`FREESOUND_TOKEN_EXPIRES_AT`（Unix秒）も保存されている場合、検索・取得時に
有効期限の60秒前からトークンを更新し、0600のファイルへ原子的に保存します。
環境変数で指定したアクセストークンは自動更新しません。更新失敗時は処理を止め、
再認証を案内します。OAuth認可画面と認証コード交換のUIは未実装です。

「公式サイトから検索して取り込む」で検索し、作品ページと利用条件を確認して「選ぶ」を押します。
音源の種類とジャンルを設定し、利用条件の確認後「この音源を取得・解析して保存」を押します。
最大10件を検索し、一括ダウンロードや自動再試行は行いません。
Jamendoは `audiodownload_allowed=true` の作品に限り、FLACの取得URLを要求します。
取得直前に作品情報を再取得し、ライセンスが変わっていれば止めます。取得した出典情報と日時も保存します。
Freesound／JamendoのHTTPSドメイン内だけで取得し、別ホストへ転送するときは認証ヘッダーを外します。
ダウンロード許可は、あらゆる二次利用の許諾を意味しません。作品とAPIの用途条件は利用者が確認します。

仕様参照: [Freesound認証](https://freesound.org/docs/api/authentication.html)、
[Freesound取得](https://freesound.org/docs/api/resources_apiv2.html#download-sound-oauth2-required)、
[Jamendo tracks](https://developer.jamendo.com/v3.0/tracks)。

### 取得済みファイルの追加と比較

1. ファイルを選択（または絶対パスを入力）し、タイトルと出典を指定します。
2. 完成曲・ステム・ループ・ワンショットを区別し、必要ならジャンルを付けます。
   既存の1,020ジャンルを使い、複数はカンマ区切り、未分類でも保存できます。
3. 作者・利用条件を記録します。Freesound／Jamendoでは公開作品ページURLも必須です。
   条件は利用者の申告として記録し、サイトの許諾を自動確認したとは扱いません。
4. 利用条件の確認欄にチェックし「ローカル解析して保存」を押します。
5. 「見る」で測定値・BPM候補・出典・解析条件を確認し、分類、確認済みBPM、試聴メモを修正できます。
6. 「この音源を比較対象にする」→「比較する」で、同ジャンル・同種類の参考音源との差を表示します。

FFmpeg / ffprobe がPATH上に必要です。自動インストールはしません。
対応形式はWAV・MP3・FLAC・AIFF・M4A・OGG（実際のデコード可否はFFmpegによる）、
上限は1ファイル256MB・30分、モノラルまたはステレオです。暗号化された音源は扱いません。
元ファイルは変更せず、管理用コピーを保存します。同じバイト内容はSHA-256で重複を判定し、
同一出典の再取り込みでは既存の分類やメモを上書きしません。別出典は同じ音源に紐付けられます。

保存先は通常 `~/Library/Application Support/KIHACHI/references/` です。
`library.sqlite3` に音源識別・出典・解析履歴・分類・メモを保存し、`audio/` に管理用コピーを保存します。
`KIHACHI_REFERENCE_DIR` で保存先を指定できます。バックアップする場合はStudioを停止し、
このフォルダ全体をコピーしてください。Gitには音源・DBを追加しません。

測定は**波形・スペクトル等の信号分析ベース**です。
LUFS・True Peakは元音源に対してFFmpegで測り、正規化音源は出力しません。
RMS・左右相関・帯域比率・パワースペクトル重心は22.05kHzへ変換した信号から計算します。
帯域比率の分母は20Hz〜10kHzのエネルギーで、境界は250Hz・2kHz、FFT窓2048・hop512です。
10秒区間のRMSも保存します。これはIntro／Dropなどの自動区間認識ではありません。
3秒未満と無音はLUFS比較対象外、8秒未満はBPM候補を出しません。
BPMはスペクトル変化の自己相関による60〜200の候補で、周期性スコアは正解確率ではありません。
一定音の微小な周期誤差を除くため、相対スペクトル変化が0.02以下のフレームを発音候補から外します。
音源・解析版・FFmpeg版・設定を残し、将来の解析版と結果を区別します。

比較はバイト内容の重複と対象音源自身を除外し、指標ごとの有効件数・中央値・範囲・差を出します。
未測定値は0として扱いません。登録曲の分布であり、ジャンル全体の標準や音楽的な品質評価ではありません。
音色選びには明るさの指標／低域比率の並べ替えを使えます。MIDI向けには**人が確認したBPMだけ**の
中央値をコピー用の制作指示にできます。自動ノート採譜、キー推定、ステム分離、生成への自動反映、
音色レシピやLiveへの書き込みは行いません。

## 適用時の保護

- 初回は `KIHACHI Kick/Hats/Bass/Stab <候補ID> [KIHACHI]` の新規トラックへ置きます。
- 新しいSessionシーンは開始小節の昇順で末尾に追加します。パートごとに通信上限による分割位置が違っても順序を保ちます。同じセクション名・開始小節のシーンは共有します。既存シーンの移動や、パート間の分割位置の統一は行いません。
- 利用者所有のクリップは置換しません。
- 録音中・再生中は停止します。
- 同じ候補の二重適用は拒否します。タイムアウト後も自動再試行しません。Studio を再起動しても、適用を試した記録は残るので拒否は続きます。
- 部分適用は成功分と失敗分を分けて表示します。残りは手動で Live の Undo を使って戻してください。
- 既存のTEST曲は触りません。適用に失敗した `[KIHACHI]` トラックは自動削除しません。LiveのUndoか、名前に候補IDが付いたトラック／シーンだけを手で消してください。

## アレンジメントへの展開

Session へ適用した候補は、「展開内容を確認」→「この内容でアレンジメントに展開」でアレンジメントビューへ並べられます。

- 各 Session クリップを、候補の小節位置のままアレンジメントへ複製します。クリップにはその区間のノートが全部入っているので、並びは確認したノートと同じです。置いたクリップのノート数も読み戻して照合します。
- Intro / Build / Drop / Outro の頭に `<セクション> <候補ID> [KIHACHI]` のロケーターを置きます。同じ位置に別名のロケーターがあると、その操作は失敗として止まります。既存のロケーターは消しません。
- 置く範囲に既存のアレンジメントクリップがあれば、何も置かずに中止します。
- Session のシーンやクリップを消した後は、複製元がないため展開できません。候補を作り直して適用してください。
- 再生中・録音中は拒否します。展開を試した候補には `<候補ID>.arranged` を置き、再起動後も二重展開を拒否します。

## 音源

Drum Rack は空のまま載せると無音です。Live 12.4 以降では、候補が使うパッドのうち空いているものへ KIHACHI 同梱のワンショットを自動で入れます。同梱はキック 36、サイドスティック 37、スネア 38、クラップ 39、クローズドハット 42、オープンハット 46、ライド 51 の7音で、どれもこのリポジトリ内で合成したものです。既に何か入っているパッドは上書きしません。12.4 未満、または読込に失敗した場合は手動案内に分けます。

Studio を再起動して候補が画面から消えた場合は、「適用済みトラックにサンプルを入れる」にトラック名の8桁（例: `KIHACHI Kick ababf584 [KIHACHI]` の `ababf584`）を入れて押します。入れるのは同梱のワンショットがある Kick=36 と Hats=42 の空パッドだけです。再生中は止まります。

## ジャンル

制作指示に書かれたジャンル名は、1020件のジャンルデータベースから規則で読み取ります（AI の推測より優先）。読み取ったジャンルの系統ごとに、次が変わります。

- ドラム: 4つ打ち、one drop（レゲエ）、ブレイクビーツ、2ステップ、ブーンバップ、スウィングするライド、サンバ、クラーベなど。スネアかクラップか、ハットの細かさも系統に従います。
- 上物: 短いスタブ、裏拍のスカンク、伸ばすパッドなど、鳴らし方と長さ。コードを変える間隔。
- ベース: 主役・脇役に応じた音の数と強さ。
- スイング: ジャズ系は裏拍 0.58、12/8 と書かれたブルース系は3連。
- ダブテクノ: 上物を裏拍の短いコードにし、付点8分で小さくなる繰り返しを付けます。指示に「ディレイ」「エコー」があれば、ほかのジャンルでもところどころに同じ繰り返しを入れます（エフェクトではなく MIDI の音符です）。

## 音色レシピ

ジャンルに音色レシピがあると、適用時に次を自動で行います（今は dub techno のみ）。

- ベースと上物に決まった純正シンセとエフェクトを挿し、つまみを名前で設定します（例: 上物は Wavetable + Echo、ベースは Analog）。値はレシピに書かれたデータで、AI は選びません。
- 指示の音の言葉（煌びやか／こもった、長め／短め、ディレイ多め／控えめ、「かなり」で2段階）は、規則で読み、読めなければローカルの AI が -2〜+2 で補います。レシピが決めた範囲のつまみだけを動かします。
- Live の Control Surface で `AbletonGPT_MCP` を選んでいると、Kick と Hats には AbletonGPT の Remote Script 経由で付属キット（909 Core Kit など）を読み込みます。選んでいなければ Drum Rack と同梱サンプルを使い、そのことを確認画面に出します。キットの読み込みは適用が verified のあとに1回だけ行い、再試行しません。
- レシピが本物の Echo を挿すジャンルでは、MIDI の繰り返しは入れません（ディレイの二重がけを防ぐため）。

すべてローカルで動き、有料 API は使いません。

## 候補の保存

生成した候補は `~/Library/Application Support/KIHACHI/candidates/<候補ID>.json` に保存し、再起動後は最後の候補を画面に戻します。ノートを含めてそのまま保存するので、確認したノートと適用するノートは再起動をまたいでも一致します。ファイルのノートが書き換わっていた場合は読み込みません。適用を試した候補には同じ場所に `<候補ID>.applied` を置き、二重適用を防ぎます。不要になった候補はこのフォルダから手で消してください。

## 残している制限

- 完成音声・歌声・自動マスタリング・追加学習は対象外です。
- mood の「暗い」は低音域と短調和声として解釈します。任意の音色名は未対応です。
- Intel Mac ではGPU加速を前提にしません。初回推論はモデル読込で十数秒かかることがあります。
- 大きな Live Set の全状態取得はタイムアウトすることがあります。その場合は適用せず、原因を表示します。

### 参考音源DBからBPMを提案

Studioの制作指示欄で「参考音源DBからBPMを提案」を開き、参考ジャンルと
音源の種類を選びます。「BPM提案を確認」で確認済みBPMの件数・中央値と追記案を表示し、
「このBPMを制作指示に追記」を押した場合だけ反映します。その後、通常の候補生成へ進みます。
元の指示にBPMやテンポに関する指定があれば変更しません。提案表示後に入力を編集した場合は
再確認が必要です。推定BPMは使わず、中央値が60〜180の場合だけ整数に丸めて提案します。
確認値なし・範囲外の場合は理由を表示します。これは登録サンプル由来の参考値であり、
ジャンルの推奨テンポ、ノート抽出、音色選択やミックスの自動変更を意味しません。

### ミックス比較で表示する測定差

対象音源を選び、同じジャンルと種類で比較すると、対象自身と同一音声の重複登録を
集計から除外します。参考音源が2件以上あり、対象と参考の両方で計測できた指標について、
LUFS、True Peak、低・中・高域の比率、スペクトル重心、左右相関の差を文章でも表示します。
例：「低域の比率: 対象と参考中央値の差は+12.0ポイント［3件］」。
この文章は測定値の記述だけで、EQ操作・マスタリング推奨・音色の良否判定ではありません。
曲の構成や楽器の違いでも数値は変わるため、試聴と併せて判断してください。

### 独自ジャンル名

参考音源DBでは、既存ジャンルにない英数字のジャンル名も登録できます。
`Mutashon Funk` は確認済みの別表記として `Mutation Funk` に対応させ、旧表記で保存済みの音源も読み取り時に同じジャンルとして集計します。元のDB表記は書き換えません。`Funk` は別ジャンルとして扱います。
Mutation Funk の新しい候補は、4つ打ちの共通パターンではなく、2小節で変わるキックとベース、弱いゴーストノート、シンコペーションのあるコードで組み立てます。ベースとコードは1曲で同じコード進行を共有します。Dropのコードは8小節中2小節を休み、休む位置は候補のシードで変わります。新規Liveトラック用にはAnalogの短いベースとWavetableの短いコードの試作音色を用意しました。これは参考音源の音符や音色を抽出したものではありません。既存候補とLive上の曲は変更されず、新しい候補で試聴して音楽的に判断します。
試聴フィードバックを受け、Mutation Funk の96小節の新規候補は Intro 8 → VerseA 16 → VerseB 16 → ChorusA 16 → Break 8 → ChorusB 16 → Outro 16 を既定構成とします。A/Bでは異なる和声機能を使い、サビではコード進行と上音域のLeadを増やし、Breakでは大半のKickとLeadを止めて最後に戻します。Kickには従来の短いサンプルを上書きせず、低域の余韻が長い `kihachi-kick-deep.wav` を新規候補に使います。これらは生成規則と信号量の変更であり、参考曲の音符を採譜したものでも、音楽的な完成を保証するものでもありません。
音声で「ビーピーエム125」と入力した場合も125 BPMの明示指定として保持します。確認済みBPMを持つMutation Funk参考曲はまだないため、参考音源DBからテンポを自動確定しません。
曲名からジャンルを推定したり、独自ジャンルをMIDI生成エンジンの既知ジャンルへ
自動で置き換えたりしません。作品の作者・ライセンス・確認済みBPMは別々の申告値です。

### BPM候補を確認する

参考音源の「見る」を開くと、解析で得たBPM候補と周期性を確認できます。
候補ボタンは「確認済みBPM」欄へ数値を入力するだけで、保存はしません。
倍・半分などの候補を元音源の再生またはDAWで確認し、
「このBPMを実際に聴くかDAWで確認しました」にチェックしてから
「分類・確認値を保存」を押します。チェックなしでのUI保存は拒否します。
参考ジャンルのBPM提案には、保存された確認済みBPMだけを使います。

保存した音源の一覧には、BPM候補と確認済みBPMを別の列で表示します。
候補が複数出る曲は、最初の数値を自動で採用しません。

「見る」の試聴プレーヤーはDB内に保存した音源のコピーをローカル再生します。
再生データは同じStudio画面へ範囲指定で送られ、外部APIへは送信しません。
再生を止めたときは処理を中断し、自動再試行しません。試聴だけでBPMを確定できない
場合はDAWで拍位置を確認してください。
# サンプル集のファイル名索引

参考音源画面では、指定した絶対パスのWAV／MP3などをファイル名で索引化し、キック・ハイハット・スネア・クラップを検索できます。索引はローカルSQLiteにパス、名前、容量、推定役割だけを保存し、元音声の複製や解析は行いません。役割はファイル名・フォルダ名からの推定であり、実際の音色を保証しません。候補を参考音源DBへ登録する場合は、フォームで利用条件を確認したうえで個別に取り込んでください。

ワンショットを登録するときは、耳で確かめた役割をキック・ハイハット・スネア・クラップ・その他から選べます。ジャンル、音源の種類、役割をそろえた比較に使い、分類の修正も可能です。役割を未指定にした従来データも引き続き閲覧・比較できます。
