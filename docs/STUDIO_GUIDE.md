# STUDIO GUIDE

制作画面（http://127.0.0.1:8765/）の各欄の説明です。既存の制作画面を拡張したもので、見た目と操作の流れは従来どおりです。起動と基本は [STUDIO.md](STUDIO.md)、最短手順は [QUICKSTART.md](QUICKSTART.md)。

## 上部の状態表示

`Ollama` / `Live` / `AbletonGPT` / `Project` / `生成` を、色だけでなく `READY` / `WARNING` / `OFFLINE` の言葉で表示します。

| 表示 | 例 | 意味 |
| --- | --- | --- |
| Ollama: READY | `gemma4:latest` | AI 解釈が使えます |
| Ollama: OFFLINE | | 既定解釈で制作を続けられます |
| Live: READY | `Live 12.4.5 / kihachi-live-device/0.3.5` | 送信できます |
| AbletonGPT: WARNING | 接続できますが応答しません | Live のダイアログが開いていないか確認 |
| Project: READY | 候補ID | 選択中の候補があります |

## JARVIS（画面の先頭）

話すか文字で依頼し、「聞く」で送ります。曲の状態、変更案、「もっと Dub っぽく」のような音楽の判断は Jarvis が返し、「計画」に目的・読むもの・書き込み案・危険度・状態を出します。書き込み案は承認が必要で、この欄からは実行しません。「後半のハット多くない？」のような質問には、その範囲の1小節あたりの音数を、範囲の外と比べて答えます。分かるパートは、キック・スネア・ハット・オープンハット・パーカッション・サブ・ベース・スタブ・パッド・アルペジオ・ギター・ホーン・リード・ボーカルです。「33-48小節のハットを減らして」のような変更案は、「この変更案を修正案にする」で下の「修正案」に出せます。範囲内の音を1つおきに抜くか、消せます。増やすのはハットだけで、音と音の間に弱めの音を足します。「後半のハットを増やして」のように前半・後半・リエントリーでも指定でき、範囲は開いている曲から決めます。「承認」欄の「保留中の操作」には、採用待ちの修正案と、承認済みでまだ送っていないパート計画が並びます。修正案はそこでも採用・却下できます。制作の相談は「提案を制作指示に反映」で、すぐ下の制作指示へ入れます。反映するまで制作指示と Live は変わりません。

## Astraへ送るパラメーター・パートの計画

- 「Astraへ送る」: ジャンル・雰囲気・指示は音の方向だけです。最初のクリックは料金の確認だけです。同じ内容でもう一度押すと有料で MIDI 候補を作ります。Live は変えません。
- 「計画を確認」: 選んだ役割、キー、テンポ、小節で、画面の中だけで計画を組みます。ジャンル・雰囲気・指示は方向として表示します。この確認のノートは変えません。全パートなら、パートごとにトラックを分けます。
- 「この計画を承認」「承認しない」: 承認は計画のハッシュに結びます。入力を変えると承認は使えません。
- 「読み戻しを確認」: 承認済みの計画を、Studio の中の偽の Set で試します。Live を読む前の計画は偽の Set に合わせ直すので、もう一度承認が要ります。偽の Set が計画どおり応答しても、実機の結果でも音の完成でもありません。
- 「実機の Live に送る」: 再生と録音を止めてから押します。1回目は実機の Set を読み、トラックとシーンを末尾に置き直すだけです。もう一度承認してから2回目を押すと、1回だけ送って読み戻します。読んだあと15分で期限切れです。同じ名前のトラックがあるときは送りません。音源は入れないので、送ったトラックに音源を載せてから聴きます。保存はしません。

## 制作指示・解釈

制作指示に入力された自然言語（日本語）は、規則ベースのパーサーとローカルAI（Ollama）によって解釈されます。

### 指示ごとの反映（カバレッジ表示）

制作指示の各文が規則で読まれ、どのように扱われたかを7つの状態で表示します。

| 状態バッジ | 意味 | 表示条件・動作 |
| --- | --- | --- |
| `反映` (緑) | 規則で読まれ、要求が反映された | テンポ、キー、小節数などの一般項目は規則による認識を示し、中間Breakなどは候補生成後の構成データで実際の配置結果まで確認して表示します（Ableton Live実機への適用確認ではありません）。 |
| `一部のみ` (黄) | 一文の中に複数の要求があり、一部のみが反映された | 同じ文に成功した要求と失敗した要求、または未確認の要求が混在する場合（例: 「16小節で中間にブレイクを入れて」）など |
| `認識済み・適用未確認` (黄) | 指示は認識されたが、候補生成前のため構成への適用が未確認 | 候補生成前の「中間にブレイクを入れて」など |
| `否定として認識（変更なし）` (緑) | 否定表現として認識し、変更を行わないことで意図を尊重した | 「上物は煌びやかにしない」「ドロップは派手にしない」など |
| `ジャンル既定で含む` (黄) | 指示で追加したのではなく、選ばれたジャンルの基本パターンに元からある要素 | Mutation Funkの「ゴーストノート」など |
| `対象外` (黄) | KIHACHIが個別に対応できない範囲の要求 | 「キックだけ明るく」など特定パート単体の音色指定 |
| `未反映` (赤) | 規則で読めなかった文、または制約により構成に配置できなかった要求 | 16小節構成での単独の中間Break配置失敗など |

> **保存・再読込み時の扱い**: 現在の実装では、プロジェクトから保存済み候補を開き直した際（`/api/candidate/{id}`）も、保存された構成データ（`candidate.brief`）に基づいてカバレッジが再評価される仕様です。なお、将来のバージョン変更にわたって永続的な同一結果を保証するものではありません。

### パート・セクション別の反映ルールと入力例

曲全体の一括変更だけでなく、対象パートやセクションを限定した指定に対応しています。

#### 1. ベースの段階変化と高密度リズム
ベースに対する指示は、時間変化と全編密度の2種類があります。
- **段階変化（音数の時間変化）**:
  - 肯定入力例: `「BASSは最初動き少なく徐々に動きのあるものへ変化する」`
  - 反映内容: 楽曲の進行度に応じて序盤のノートを間引き（フルパターンの部分集合）、後半に向けて段階的に本来のパターンへと音数を復元します。
- **高密度リズム（全編の音数増加）**:
  - 肯定入力例: `「ベースは動きを増やす」`、`「ベースの音数を多く」`
  - 反映内容: 通常パターンを生成する区間では密度の高いベースリズムを選択します。Introの発音開始、Breakの持続音、Outro終盤の無音は従来の処理を優先します。

#### 2. Subの追従条件
Sub パートは間引き後の Bass パターンから連動して生成されますが、以下の条件付きです：
- ベロシティ60未満のノート（ゴーストノート等）は除外されます。
- Break セクションおよび breakdown 指定の小節では、低域を抜くために発音自体が抑制されます。
- したがって、Bass のすべてのノートを無条件に鳴らすわけではなく、条件を満たしたノートのみが低域を補強します。

#### 3. ベースのBreak／Outro処理
- **Break**: 持続音の処理（小節頭等の長いベース音）が優先され、通常パターンの段階変化は行われません。
- **Outro**: Outro内の最後の最大8小節ではベースが発音しません。Outro が8小節を超える長い構成の場合、それ以前の小節は通常パターンとして段階的な間引き処理の対象となります。曲全体や上物を無音にする指定ではありません。

#### 4. 上物の煌びやかさ・Drop強調
- **肯定入力例**: `「上物は徐々に煌びやかに」`、`「ドロップは派手に」`
- **否定入力例**: `「上物は煌びやかにしない」`、`「ドロップは派手にしすぎない」`
- **対象パート**: 上物（Stab / Lead / Pad / Arp / Vocal / Guitar / Horn）。Drums、Bass、Sub には影響しません。
- **反映内容**:
  - 上物の煌びやかさ（徐々に）: 曲の前半1/3は変化なし、中盤1/3でトップノートの1オクターブ上（+12）を低ベロシティで追加、後半1/3でベロシティを+5強調。
  - 上物の煌びやかさ（一定）: 全セクション（Break/Outro除く）でオクターブ上のノートを追加。
  - Drop強調: Dropセクションの上物のみオクターブノートを追加し、ベロシティを+6強調。
- **例外・制限事項**:
  - **Arp パート**: オクターブ音の追加は行いません（ベロシティ変化のみ適用）。
  - **音高上限**: オクターブ上のノートが上限音高（96 / C7）を超える場合は追加されません。
  - **否定時のDrop**: 「上物は煌びやかにしない」に加えて「ドロップは派手に」と指定した場合、Dropセクションではオクターブ音を追加せず、打鍵ベロシティの強調（+6）のみを適用します。否定指定だけではDropの強調を追加しません。
- **MIDI表現の範囲と限界**: 音域の拡張（オクターブ重ね）と打鍵ベロシティの強調によるMIDIデータの変更です。シンセのカットオフ周波数、EQブースト、ディレイ/リバーブの開閉など**音色自体のパラメーターオートメーションは行わない**ため、音色の抜けやブライト化を保証するものではありません。

#### 5. 中間Breakの配置・再利用・制約
- **肯定入力例**: `「144小節のダブテクノ。中間にブレイクを入れて」`、`「中間でBreakを必ず入れ」`
- **否定入力例**: `「中間にブレイクを入れない」`
- **位置判定の定義**: 曲の中心 `(bars + 1) / 2` に対し、Breakの中心位置が `max(4.0, bars * 0.15)` 小節以内（楽曲全長の概ね 35% 〜 65% の範囲内）にあるかを位置データで判定します。
- **再利用と追加（挿入）**:
  - 144小節（Drop指定なし / Drop=57）など、中央付近に既定Breakがある場合は既存Breakを再利用（`fulfilled`）します。
  - 48小節（Drop=33）など、中央にBreakがない場合は中央（25〜28小節）に4小節のBreakを挿入し、前後セクションを分割して区間連続性と総小節数、Drop開始位置を維持します。
  - 144小節（Drop=9）など、中央から離れた位置（25〜32小節）に既定Breakがある場合、**既存Breakを勝手に移動・削除せず保持したまま**、中央の長大なDrop区間内（73〜76小節）に中間Breakを挿入します。
- **配置できない条件とカバレッジ表示**:
  - 曲が短い場合（`bars < 32`、例: 16小節構成）: 曲の長さが不足するため配置不可。
  - ドロップ位置等との干渉（32小節・Drop=17など）: 中央付近のセクション長が12小節未満で前後各4小節を確保できない場合、またはDrop開始小節と重複する場合は配置不可。
  - 配置失敗時の表示:
    - 「中間にブレイクを入れて」単独の要求なら **`未反映`** となります。
    - 「16小節で中間にブレイクを入れて」のように、同じ文に反映された別要求（小節数など）が含まれる場合は、文全体を完全反映とせず **`一部のみ`** と表示されます。

### 未対応事項
- **既定Breakの自動削除**: 「中間にブレイクを入れない」と否定指定した場合、明示的なBreakの追加は行いませんが、ジャンルテンプレート本来の既定Breakを自動削除することはしません（既定構成の安定性を優先）。
- **音色・パラメーターのオートメーション**: フィルターのカットオフやレゾナンス、エフェクトセンド等の時間変化は未実装です。
- **非対応パートの単独音色指定**: 「キックだけ明るく」など、KIHACHIが単独で音色を変更できないパート指定は対象外として通知されます。

### データの検証範囲と聴感上の限界
構造検査や単体テストで確認しているのは、ノート数・音域・強弱・小節範囲などのデータ構造の整合性です。MIDIデータの変更だけで聴感上の改善や意図通りの仕上がりを保証するものではありません。Live実機への送信や試聴を通じて、音源プリセットやMIXのバランスを確認する必要があります。

- 「AIが補った値」: AI が決めた値と、それが音に影響するかどうか。
- 「未対応・矛盾・曖昧」: 指示と AI の食い違い、AI の応答が使えなかった理由など。

## プロジェクト

「MIDI候補」の再生ボタンは、選択中の候補から最初のDropまたはChorusの最大8小節を簡易音色で再生します。保存済み候補を開いたときも同じノートから作り直し、Liveへ送信しません。音色・MIXの完成評価には使わず、フレーズと展開の確認に使います。

- 保存済みの候補の一覧（承認済・送信済の印つき）と「この候補を開く」。
- 状態行: `承認` / `Live送信` / `アレンジメント` / `検証` と、修正版なら元の候補ID。
- SongSpec: Tempo、Key、Scale、拍子、Genre、Style、Bars、長さ、Swing、AI。
- 構成: セクションごとの小節範囲、エネルギー、鳴るパート。上の帯はエネルギーの高さを表します。
- トラック: 表示名（ジャンル別。Mutation Funk なら SLAP BASS / DUB CHORDS / MUTATION SYNTH）、クリップ数、ノート数、使うセクション。

## AIレビュー

送る予定のノートを規則で調べます（音楽的な良し悪しの判定ではありません）。各指摘に重要度、小節範囲、推奨があります。

- 「選んだ指摘を修正」「すべて修正」: 指摘に対応する範囲だけを直す修正案を作ります。
- 「選んだ指摘を無視」: その候補のレビューから外します（修正対象にもしません）。
- 「範囲を指定して修正を依頼」: 対象（ベース / ドラム / ベロシティ / セクション末尾 / 構成）と小節（例 33-49）。
- 「この候補を承認」: Live へ送る前に必須です。

## 修正案

BEFORE / AFTER、変更範囲、ノート数の変化、修正後の指摘数を表示します。「採用」で新しい候補になり（再承認が必要）、「却下」で今の候補のままです。修正履歴は再起動後も残ります。

## Liveへ適用

1. 「適用内容を確認」: ABLETON PLAN（Tempo / Tracks / Clips / MIDI Notes / Arrangement と操作の内訳）。送れない理由があれば赤字で出ます。
2. 「この内容でLiveへ適用」: 1回だけ送信し、続けて読み戻し検証します。
3. 「Liveから読み戻して検証」: いつでも再確認できます。Live に接続できないときは `EXTERNAL VERIFICATION REQUIRED` と表示します。

`ABLETON VERIFICATION` の各行は `PASS` / `FAIL` / `SKIP`。テンポを変えない設定なら Tempo は SKIP、未展開なら Arrangement は SKIP です。

## エフェクト処理 / MIX / サイドチェイン / マスタリング

`PROJECT READY` の後に上から順に使います。各欄とも「〜を確認」で送る内容（トラックごとのデバイスの並び、音量とパン）を表示し、次のボタンで1回だけ送って読み戻します。Live が再生・録音中なら送りません。既存のデバイスは消さず、同じデバイスを二重に入れません。

| 欄 | 変えるもの |
| --- | --- |
| エフェクト処理 | 各トラックの音源の後ろに、パートごとの EQ・コンプ・サチュレーター・リバーブ・ディレイ |
| MIX | 各トラックの音量(dB)とパン。キックが最大、120Hz以下は中央 |
| サイドチェイン | Sub・Bass・Pad の最後に、キック（エフェクト後・フェーダー前）をキーにしたコンプ |
| マスタリング | マスタートラックの最後に EQ → Glue Compressor → Saturator → Utility（低域モノ）→ Limiter（True Peak, 天井 −1.2 dB） |

結果が `verified` 以外なら、計画値と Live の値が食い違ったつまみを一覧します。

- 「エフェクトのつまみを設定し直す」: パートにチェックを入れて確認すると、変えるつまみを Live の目盛りの単位（Hz / dB / % など）で一覧します。送るのは確認した内容そのもので、確認後にチェックを変えたら確認し直しが必要です。デバイスの追加・削除はしません。
- 「マスタリング」の「つまみを設定し直す」にチェックを入れて確認すると、マスターのつまみを同じ形で一覧します。
- 「音圧を測る」: 書き出した WAV / AIFF / FLAC のパスを入れると、Integrated / Short-term max / Loudness range / True Peak / PLR / 120Hz以下の比率と、選択中の候補のセクション別音圧を表示します。Live には触れず、音声ファイル以外は読みません。

## システム（状態・設定・診断）

- 診断: Python、依存関係、設定、保存先、Ollama、モデル、MCP、AbletonGPT、Remote Script、Live、Studio を一覧し、各行に対処を出します（`uv run kihachi doctor` と同じ内容）。
- AI: 通常はOllama。OpenAIはSol/Astraを明示選択した場合だけ使い、次回推定額・月間累計・月間上限（初期値500円）を表示します。APIキーは`OPENAI_API_KEY`環境変数だけから読み、設定ファイルには保存しません。
- GPT-6 APIを使う場合: 既存のStudioを終了し、`scripts/kihachi-studio-gpt6.command`を開きます。ターミナルにAPIキーを入力しても文字は表示されません。キーはその起動プロセスの環境変数として渡され、Studioの設定ファイルには保存されません。Studioの「システム」でAIをOpenAI、モデルをSolまたはAstraに変更します。生成ごとに料金を確認して承認するまで有料APIは呼び出しません。通常のOllama起動には`kihachi-studio.command`を使います。月間上限はStudio内の推定額に対する制御であり、OpenAIアカウントの請求上限ではありません。
- OpenAIを選んで「保存」した後に「OpenAI接続テスト」を押すと、キーと選択モデルへのアクセスを読み取り専用のモデル情報取得で確認します。生成リクエストと料金は発生しません。「Ollama接続テスト」はローカルOllama専用です。Studioを更新した後は、Studioを終了してGPT-6用ランチャーから起動し直してください。
- Ableton / Project: ポートと保存先。保存先は `KIHACHI_PROJECT_DIR` で変えられます。
- Abletonの「利用可能な操作」は、現在のBridge契約を`SUPPORTED / CONDITIONAL / UNSUPPORTED`で表示します。`OFFLINE`の機能と`UNSUPPORTED`の操作はAIへ実行可能として渡しません。
- MIDI Composerは構造化されたキー、テンポ、小節、役割、グリッド、シンコペーション、velocity、ノート長、Kick回避条件を受け取ります。現在のStudio全曲生成は既存の決定論builderを維持し、明示選択されていない有料Composerへ自動移行しません。
- 「パート単位MIDI Composer」は、最初のボタンで制約・provider・モデル・推定料金を確認し、次のボタンでノート候補だけを生成します。入力を変更すると確認は失効します。生成しただけでは保存候補にもAbletonにも反映されません。
- 生成後の「選択中の候補へ採用案を作る」は、Bass / Stab / Lead / Arp / Percの対応パートだけを置換した子候補を作ります。BEFORE / AFTERとCritic結果を確認して採用するまで元候補は変わりません。Drumsは複数トラックへ分かれるため一括採用を拒否します。
- 開発者モード: エラーの技術的な詳細を表示します。通常は分かりやすい説明だけです。
