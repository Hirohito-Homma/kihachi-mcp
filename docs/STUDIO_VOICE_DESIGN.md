# KIHACHI Studio 完全音声対話の設計

## 目的と現状

ユーザーは日本語で制作について話し、KIHACHIは文脈を保ちながら聞き返し、提案を読み上げ、承認された操作を実行し、その結果を声と画面で返す。たとえば「Mutashon Funkで曲を作って」「キックをもう少し太く」「今の案を聴く前に変更点を教えて」「Liveに入れて」と続けて話せることを最終目標とする。画面と文字入力は音声が使えない場合の代替として残す。

2026-09-28時点でStudioにはテキストの制作指示、MIDI候補生成、参考音源DB、Live適用・アレンジのプレビューと承認処理がある。対話の最初の段階として、短い文脈保持、曖昧な指示の聞き返し、制作指示への追記案、macOS内の日本語読み上げ、ブラウザの短時間録音からオンデバイス認識へ送る経路を追加した。音声認識のMac権限許可とマイク実機での日本語精度は未確認。長期の自然な会話も未実装。Apple Speechの日本語オンデバイス対応はこのMacで確認した。追加モデルはダウンロードしていない。

## 先に決める情報

- 音声認識・読み上げ・対話処理はこのMac内だけで行う。ユーザーが2026-09-28に指定済み。音声をクラウドへ送らず、有料API・自動モデルダウンロードも行わない。
- マイクとスピーカーの対象。まずStudioを開いたMac内の入出力を想定し、Liveの音がマイクへ回り込む場合に備えて割り込み・ミュートを設ける。
- 常時待機・ウェイクワードの要否。初期版は押して話す方式にし、常時待機は別途検証する。
- 話した指示が許す操作の範囲。候補生成、参考音源検索、ミックス比較、Live変更を別権限として扱う。

## 十案と弱点

| 案 | 弱点 |
| --- | --- |
| 1. 音声を制作指示欄へ転記 | 一往復で終わり、聞き返しができない |
| 2. ブラウザだけで認識・読み上げ | 実装依存と外部処理の有無を統制しにくい |
| 3. サーバーだけで音声入出力 | Studioを開く端末のマイク・スピーカーを扱いにくい |
| 4. 毎発話を独立した命令として処理 | 「それを少し短く」などの指示対象が失われる |
| 5. 会話履歴をすべてLLMへ渡す | 長い履歴で誤解・遅延・費用が増える |
| 6. LLMの文章から直接API実行 | 誤認識と誤解釈を変更前に止められない |
| 7. すべての操作を毎回画面で承認 | 対話のテンポが悪い |
| 8. 声だけでLive変更を承認 | スピーカーからの回り込みや誤認識で誤実行し得る |
| 9. 常時待機を最初から実装 | 誤起動・回り込み・プライバシーの検証範囲が広い |
| 10. 音声入出力を交換可能な部品にし、状態付き対話から検証済み操作案を作る | 部品が増え、状態管理の実装と試験が必要 |

案10を採用する。音声エンジンを替えても会話の意味とLive安全境界が変わらない。初期操作は押して話す方式で、最終的な常時対話の可否は回り込み・割り込み試験で決める。

## 対話の流れ

1. マイク入力を一発話として取得し、無音・長さ上限・ユーザー停止を処理する。読み上げ中は入力を抑制し、ユーザーが割り込んだ場合は読み上げを止める。
2. 音声認識は原文、認識候補、時刻を返す。原文は画面に表示し、ユーザーが修正できる。音声を無断で外部送信・永続保存しない。
3. 会話管理は現在の候補ID、対象ジャンル、比較対象、未確定の操作案だけを保持する。「それ」が何か特定できなければ質問する。明示された数値はLLMに書き換えさせない。
4. 意図解釈は固定スキーマの `action / target / parameters / evidence / uncertainty` を返す。許可したアクション以外は実行しない。「太く」などの曖昧語は音色、EQ、音量のどれかを聞き返す。
5. 読み取り専用の問い合わせはすぐに答える。制作指示の変更は編集可能な案として示し、ユーザーが採用した後に候補を生成する。
6. Live変更は既存の `/api/apply/preview` や `/api/arrangement/preview` で現在状態と衝突を読み取り、対象Set、トラック、クリップ、ノート、テンポ変更の有無を読み上げ・表示する。音声による「はい」だけで実行せず、画面上で対象と操作案を確認して承認する。承認後は既存の実行ゲートを使い、readbackの結果を報告する。
7. 失敗・部分適用・接続切れは成功として言い換えず、再実行もしない。現状と人が取るべき次の操作を伝える。

## 操作案の契約

各対話ターンは `turn_id` と発話の原文を持つ。操作案には `action_id`、対象候補ID、対象Live Setの識別情報、読み取り時の状態識別子、具体的なパラメータ、必要な承認種類、有効期限、発話と画面表示に共通の要約を持たせる。会話モデルの自由文は実行APIの引数に直結しない。承認前に対象やパラメータ、Liveの状態が変われば案を無効化し、再プレビューする。

ユーザー向けの状態は `待機 → 聞き取り中 → 確認待ち → 解釈中 → 質問中／提案中 → 承認待ち → 実行中 → 結果確認` とする。画面には常に原文、現在の対象、KIHACHIがした操作、未実行の案を残す。読み上げは短くし、詳細は画面で確認できるようにする。

## 実装順と完了条件

1. 音声処理なしのテキスト対話エンジンを作る。「それ」「もう少し」などの指示対象、曖昧さ、操作案、確認状態をテストする。Live変更のAPIは呼ばない。現時点では短い文脈、曖昧さの聞き返し、制作指示への原文追記案まで実装。自然な複数ターンの意図解釈は今後の作業。
2. このMacで使える日本語の認識・合成エンジンとモデルを調査し、ネットワーク遮断下の精度・速度・メモリを実測して選ぶ。ユーザー承認なしにモデルをダウンロードしない。Apple Speechのオンデバイス指定とmacOS内の読み上げを接続した。原文表示・修正、読み上げ停止は実装。マイク権限、実際の発話、回り込み、割り込みを実機で検証する必要がある。マイク不可でもテキスト対話は使える。
3. 参考音源検索、DB比較、MIDI候補生成など読み取り・可逆操作を対話に接続する。制作指示の原文と明示数値が保たれることを確認する。
4. Liveプレビューと画面承認を接続する。プレビューと実行計画の一致、既存クリップの保護、部分適用の停止、readbackを実機で確認する。
5. 最後に常時対話を評価する。誤起動、回り込み、長時間利用、機材負荷、プライバシーを通過した場合だけ有効化する。

各段階で「実装済み」「自動テスト済み」「Macの音声入出力で確認済み」「Live実機で確認済み」を分けて報告する。数値解析や自動テストだけで音質・対話の自然さを保証しない。

## 三つの視点

- 理論重視の経済学者：音声認識から実行までの誤りが連鎖するため、各段階で不確実性を見せる。承認コストは不可逆な操作に集中させる。
- 現場主義のマネージャー：制作中の手を止めないよう、短い質問、割り込み、テキストへの切り替え、失敗からの復帰を重視する。
- 辛口な投資家：派手な常時会話より、実際に候補生成・比較・Live反映まで完遂し、誤操作を抑えた証拠を求める。

三者を統合すると、価値の中心は「会話しながら制作を完了できること」であり、音声エンジン単体のデモではない。まずテキストでも動く対話状態機械を完成させ、音声とLiveを段階的に接続する。
